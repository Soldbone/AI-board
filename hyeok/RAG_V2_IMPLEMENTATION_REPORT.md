# RAG V2 임베딩 검색 구현 보고서

## 1. 목표

기존 RAG 기능은 입력 문장에서 키워드를 뽑고, 게시글의 제목/내용/태그/댓글에 같은 단어가 포함되어 있는지를 비교하는 방식이었다.

이번 구현의 목표는 단어가 정확히 일치하지 않아도 의미가 비슷한 게시글을 찾을 수 있도록, 게시글 내용을 임베딩 벡터로 변환해서 PostgreSQL의 pgvector에 저장하고 검색에 활용하는 것이다.

## 2. 구현 범위

### 2.1 게시글 임베딩 저장 구조

게시글마다 검색에 사용할 내용을 하나의 텍스트로 합친 뒤 임베딩한다.

임베딩 대상에 포함되는 정보는 다음과 같다.

- 게시글 제목
- 게시글 내용
- 지역
- 가게명
- 카테고리
- 태그
- 최근 댓글 요약

이렇게 만든 텍스트는 `post_embeddings` 테이블에 `source_text`로 저장되고, OpenAI 임베딩 모델이 만든 벡터는 `embedding` 컬럼에 저장된다.

### 2.2 댓글 요약 반영

댓글이 너무 많아질 수 있기 때문에 모든 댓글을 그대로 임베딩하지 않고, 최근 댓글 일부만 가져와 요약 텍스트를 만든다.

현재 정책은 다음과 같다.

- 최근 댓글 최대 20개를 후보로 사용
- 중복 댓글과 너무 짧은 댓글은 제외
- 대표 댓글 최대 5개를 반영
- 댓글에서 뽑은 주요 키워드도 함께 반영

이 방식으로 댓글 수가 많아져도 임베딩 텍스트가 지나치게 커지는 문제를 줄였다.

### 2.3 자동 임베딩 갱신

게시글이나 댓글이 바뀌면 해당 게시글의 의미도 달라질 수 있으므로, 다음 작업 후에 자동으로 임베딩을 다시 만든다.

- 게시글 작성
- 게시글 수정
- 댓글 작성
- 댓글 수정
- 댓글 삭제

API 응답이 느려지지 않도록 FastAPI의 `BackgroundTasks`를 사용했다.

즉, 사용자는 글 작성 응답을 먼저 받고, 서버는 뒤에서 해당 게시글의 임베딩을 저장한다.

### 2.4 벡터 기반 유사 게시글 검색

사용자가 글을 작성할 때 입력한 제목, 내용, 태그를 하나의 검색 텍스트로 합친다.

그 검색 텍스트를 같은 임베딩 모델로 벡터화한 뒤, DB에 저장된 게시글 벡터들과 cosine distance를 비교한다.

거리가 가까운 게시글일수록 의미가 비슷한 게시글로 판단한다.

### 2.5 기존 키워드 RAG fallback 유지

OpenAI API 키가 없거나, 아직 임베딩된 게시글이 없거나, 벡터 검색에서 결과가 나오지 않을 수 있다.

이 경우 서비스가 실패하지 않도록 기존 키워드 기반 RAG 검색으로 자동 fallback하도록 만들었다.

## 3. API 동작 방식

### 3.1 `POST /ai/similar-posts`

프론트에서 기존처럼 호출하는 기본 유사 게시글 API다.

동작 순서는 다음과 같다.

1. 입력값을 임베딩한다.
2. pgvector로 유사 게시글을 검색한다.
3. 결과가 있으면 벡터 검색 결과를 반환한다.
4. 결과가 없거나 벡터 검색이 실패하면 기존 키워드 RAG 결과를 반환한다.

### 3.2 `POST /ai/vector-similar-posts`

벡터 검색을 명시적으로 테스트할 수 있는 API다.

현재는 `/ai/similar-posts`와 같은 로직을 사용한다.

### 3.3 `POST /ai/rag/similar-posts`

기존 키워드 기반 RAG만 테스트할 수 있는 API다.

벡터 검색과 키워드 검색 결과를 비교하고 싶을 때 사용할 수 있다.

## 4. 수정된 주요 파일

### 4.1 `backend/app/services/embedding_service.py`

임베딩 관련 핵심 로직을 담당한다.

추가된 주요 기능은 다음과 같다.

- OpenAI 임베딩 생성
- 게시글 임베딩 source text 생성
- 댓글 요약 생성
- 게시글 ID 기준 자동 임베딩 저장
- 검색어 임베딩 생성
- pgvector cosine distance 기반 유사 게시글 조회

### 4.2 `backend/app/routers/ai.py`

AI 관련 API 라우터다.

기존 유사 게시글 API를 벡터 검색 우선 방식으로 변경했다.

단, 기존 키워드 RAG만 확인할 수 있도록 `/ai/rag/similar-posts`는 따로 유지했다.

### 4.3 `backend/app/routers/posts.py`

게시글 작성과 수정이 끝난 뒤 백그라운드에서 임베딩을 다시 만들도록 연결했다.

### 4.4 `backend/app/routers/comments.py`

댓글 작성, 수정, 삭제가 끝난 뒤 해당 게시글의 임베딩을 다시 만들도록 연결했다.

댓글 내용도 유사 게시글 검색 품질에 영향을 주기 때문이다.

## 5. 전체 동작 흐름

### 5.1 게시글 저장 흐름

1. 사용자가 게시글을 작성한다.
2. FastAPI가 게시글과 태그를 DB에 저장한다.
3. API는 사용자에게 응답을 반환한다.
4. 백그라운드 작업이 실행된다.
5. 게시글 제목, 내용, 태그, 댓글 요약을 하나의 텍스트로 합친다.
6. OpenAI `text-embedding-3-small` 모델로 임베딩 벡터를 만든다.
7. `post_embeddings` 테이블에 벡터를 저장한다.

### 5.2 유사 게시글 검색 흐름

1. 사용자가 글쓰기 화면에서 제목, 내용, 태그를 입력한다.
2. 프론트가 `/ai/similar-posts`를 호출한다.
3. 백엔드가 입력값을 임베딩 벡터로 변환한다.
4. pgvector가 기존 게시글 벡터들과 거리를 비교한다.
5. 가장 가까운 게시글들을 유사 게시글로 반환한다.
6. 벡터 검색이 실패하면 기존 키워드 RAG 검색 결과를 반환한다.

## 6. 검증 결과

### 6.1 문법 검사

다음 명령으로 Python 문법 검사를 통과했다.

```powershell
.\.venv\Scripts\python.exe -m compileall app scripts
```

### 6.2 API 응답 확인

`POST /ai/similar-posts` 호출 결과 정상적으로 게시글 목록이 반환되었다.

응답의 `matched_fields` 값이 `["vector"]`로 내려와 실제 벡터 검색 경로가 사용된 것을 확인했다.

### 6.3 기존 RAG API 유지 확인

`POST /ai/rag/similar-posts`도 정상 응답했다.

따라서 벡터 검색과 기존 키워드 RAG를 분리해서 비교할 수 있다.

## 7. 남은 개선 포인트

현재 구현은 2주 프로젝트와 발표 데모를 기준으로 적절한 MVP 수준이다.

추후 운영 수준으로 확장한다면 다음을 고려할 수 있다.

- 백그라운드 작업을 FastAPI `BackgroundTasks` 대신 Celery, RQ 같은 작업 큐로 분리
- 대량 게시글 임베딩을 batch 단위로 처리
- OpenAI API 실패 시 재시도 정책 추가
- 조회수, 댓글 수, 최신성을 벡터 검색 점수에 함께 반영
- 댓글이 매우 많은 게시글은 LLM 요약을 별도 저장
- 게시글 삭제 시 임베딩 row도 soft delete 또는 삭제 처리

## 8. 정리

이번 단계에서 RAG는 단순 키워드 매칭을 넘어, 게시글의 의미를 벡터로 저장하고 비교하는 구조로 확장되었다.

사용자가 작성 중인 글과 의미가 가까운 게시글을 추천할 수 있게 되었고, 기존 키워드 RAG fallback도 유지했기 때문에 데모 안정성도 확보했다.
