과제 요구사항과 연결해서 보기

백엔드는 게시판 기능과 AI 응용 기능을 연결하는 중심 시스템이다.

이 자료는 과제 페이지의 요구사항을 기준으로, 우리 프로젝트의 백엔드가 어떤 역할을 하는지 이해하기 위한 학습용입니다. 문법보다 요청 흐름, 데이터 흐름, RAG, MCP, Agent가 왜 필요한지를 중심으로 보면 됩니다.

1
Request 프론트엔드나 사용자가 서버에 요청을 보냄
2
Controller 요청 주소와 방식을 보고 어떤 기능인지 판단
3
Service 실제 규칙, 검증, 데이터 처리 흐름을 담당
4
Database / API 필요한 데이터를 저장하거나 외부 정보를 조회

과제 요구사항을 먼저 해석하기

이번 과제의 핵심은 “프론트엔드, 백엔드, 데이터베이스, AI 응용기술을 직접 설계하고 구현해보는 경험”입니다. 따라서 기능을 만들었다는 사실보다, 왜 그런 구조로 만들었는지 설명할 수 있어야 합니다.

프론트엔드: React

사용자가 게시글을 쓰고, 검색하고, AI 기능을 실행하는 화면을 담당합니다.

백엔드: NestJS

요청을 받고, 인증과 권한을 확인하고, DB와 AI 기능을 연결하는 중심 역할입니다.

데이터베이스: PostgreSQL

사용자, 게시글, 댓글, 태그, AI 추천 결과와 근거 데이터를 저장합니다.

LLM: 상용 모델

직접 모델을 만드는 대신, 완성된 모델을 서비스 기능 안에서 활용합니다.

이 과제에서 AI 기능이 중요한 이유

과제는 단순 게시판이 아니라 AI 웹 애플리케이션을 요구합니다. 그래서 기본 CRUD 위에 RAG, MCP, Agent가 각각 다른 방식으로 붙습니다. RAG는 내부 데이터를 LLM과 연결하고, MCP는 외부 시스템을 LLM이 사용할 수 있게 하며, Agent는 여러 도구를 순서대로 실행하는 흐름을 관리합니다.

  1. 1
    기본 게시판
    회원가입, 로그인, 게시글, 댓글, 태그, 페이징, 검색으로 서비스의 기본 뼈대를 만듭니다.
  2. 2
    RAG 기능
    게시글과 댓글을 근거 데이터로 활용해 AI 추천의 품질과 설명 가능성을 높입니다.
  3. 3
    MCP 기능
    식품 영양정보 같은 외부 데이터를 표준화된 방식으로 가져와 AI 기능의 근거를 보강합니다.
  4. 4
    Agent 기능
    재료 추출, 영양정보 확인, 글 평가, 초안 재작성 같은 여러 단계를 하나의 추론 흐름으로 묶습니다.

NestJS에서 역할을 나누는 이유

백엔드가 커질수록 중요한 것은 “어디에 무엇을 둘 것인가”입니다. NestJS는 기능을 역할별로 나누도록 도와줍니다.

Module

관련된 기능을 하나의 묶음으로 정리합니다. 인증, 게시글, 댓글처럼 영역을 나누는 기준입니다.

Controller

사용자의 요청이 들어오는 입구입니다. 주소와 요청 방식을 기준으로 기능을 연결합니다.

Service

실제 작업이 일어나는 곳입니다. 데이터 조회, 저장, 권한 확인, 외부 API 호출 같은 일을 맡습니다.

DTO

요청으로 들어오는 데이터의 모양을 정합니다. 서버가 기대하는 입력값의 약속입니다.

생각 포인트: Controller가 모든 일을 직접 하면 처음에는 쉬워 보이지만, 기능이 늘어날수록 수정하기 어려워집니다. 그래서 요청의 입구와 실제 처리 로직을 나눕니다.

인증과 JWT

인증은 “이 사용자가 누구인지 서버가 믿을 수 있게 확인하는 과정”입니다. 이 프로젝트에서는 회원가입, 로그인, 토큰 검증 흐름으로 나뉩니다.

회원가입 흐름

  1. 1
    이메일 중복 확인
    이미 가입된 이메일인지 먼저 확인합니다.
  2. 2
    비밀번호 해시
    비밀번호 원문을 저장하지 않고, 해시된 값만 저장합니다.
  3. 3
    사용자 저장
    이메일, 닉네임, 해시된 비밀번호를 데이터베이스에 저장합니다.

로그인 흐름

  1. 1
    사용자 찾기
    이메일을 기준으로 가입된 사용자를 찾습니다.
  2. 2
    비밀번호 비교
    입력된 비밀번호가 저장된 해시와 맞는지 확인합니다.
  3. 3
    토큰 발급
    로그인 이후 요청에서 사용할 JWT를 발급합니다.
핵심 개념: 서버는 비밀번호를 기억하는 것이 아니라, 비밀번호가 맞는지 확인할 수 있는 안전한 흔적만 저장합니다.

게시글과 댓글 흐름

게시판 기능은 백엔드 기본기를 익히기에 좋습니다. 조회, 생성, 수정, 삭제와 권한 확인이 모두 들어 있기 때문입니다.

게시글에서 보는 핵심 개념

  • 목록 조회는 많은 데이터를 간단히 보여주는 흐름입니다.
  • 상세 조회는 한 게시글의 전체 내용을 보여주며, 조회 수도 증가합니다.
  • 작성, 수정, 삭제는 로그인한 사용자 정보가 필요합니다.
  • 수정과 삭제는 작성자 본인인지 확인해야 합니다.

댓글에서 보는 핵심 개념

  • 댓글은 특정 게시글에 종속됩니다.
  • 댓글 작성 전에는 대상 게시글이 존재하는지 확인해야 합니다.
  • 댓글 수정과 삭제도 작성자 권한 확인이 필요합니다.
  • 게시글이 삭제되면 연결된 댓글도 함께 정리될 수 있습니다.

데이터 관계 이해하기

백엔드를 제대로 이해하려면 “기능이 어떤 데이터를 만들고, 어떤 관계를 바꾸는가”를 같이 봐야 합니다.

User 게시글, 댓글, AI 추천 요청의 주체입니다.
Post 사용자가 작성한 게시글이며, 댓글과 태그를 가질 수 있습니다.
Comment 게시글에 연결되는 반응 데이터입니다.
Tag 게시글을 분류하고 검색을 돕는 짧은 이름입니다.
RAG Document AI 추천이 참고할 수 있도록 게시글을 의미 단위로 저장한 자료입니다.
AI Recommendation 사용자 요청과 기존 게시글 근거를 바탕으로 생성된 추천 결과입니다.
질문해볼 지점: 게시글 내용이나 댓글이 바뀌면, 이전 AI 추천 결과를 그대로 믿어도 될까요? 이 프로젝트에서는 그런 경우 추천 결과를 오래된 정보로 볼 수 있게 관리합니다.

RAG와 MCP를 먼저 구분하기

이 과제에서 AI 기능을 제대로 설명하려면 RAG, MCP, Agent를 한 덩어리로 외우면 안 됩니다. 셋은 모두 LLM을 더 유용하게 만들지만, 해결하는 문제가 다릅니다.

기술 핵심 질문 우리 프로젝트에서의 역할
RAG LLM이 무엇을 근거로 답하게 할 것인가? 게시글, 댓글, 태그를 검색해서 레시피 추천의 근거로 사용합니다.
MCP LLM 또는 Agent가 외부 시스템을 어떻게 호출하게 할 것인가? 공공 식품 영양정보 API를 도구처럼 호출할 수 있게 연결합니다.
Agent 여러 도구를 어떤 순서로 실행하고 상태를 어떻게 관리할 것인가? 재료 추출, 영양 분석, 글 평가, 초안 재작성을 단계적으로 실행합니다.
공부할 때는 이렇게 나누면 좋습니다. RAG는 “근거 검색”, MCP는 “외부 도구 연결”, Agent는 “도구 실행 흐름 관리”입니다.

RAG 자세히 이해하기

RAG는 Retrieval-Augmented Generation의 줄임말입니다. 말 그대로 먼저 검색하고, 그 검색 결과로 LLM의 생성을 보강하는 방식입니다.

왜 RAG가 필요한가

LLM은 문장을 자연스럽게 만들 수 있지만, 우리 서비스 안에 있는 최신 게시글이나 댓글을 자동으로 알고 있지는 않습니다. 게시판에 어떤 재료 질문이 올라왔는지, 댓글에서 어떤 조리 팁이 나왔는지, 어떤 글이 비슷한 상황인지 알게 하려면 LLM에게 관련 자료를 넣어줘야 합니다.

RAG는 이 문제를 해결합니다. LLM이 답하기 전에 서비스 내부 데이터를 검색하고, 그 결과를 “참고 자료”로 넘겨줍니다. 그래서 AI 추천은 단순한 상상 답변이 아니라, 커뮤니티 데이터와 연결된 답변이 됩니다.

RAG 전체 흐름

1. 데이터 수집
게시글 제목, 본문, 댓글, 태그, 조회 수 같은 데이터를 추천용 문서로 묶습니다.
2. 문서화
LLM이 참고하기 좋은 형태로 글의 상황, 재료, 댓글 조언, 태그를 정리합니다.
3. 임베딩
문서의 의미를 숫자 벡터로 바꿉니다. 의미가 비슷한 글은 벡터 공간에서도 가까워집니다.
4. 벡터 저장
PostgreSQL의 pgvector 컬럼에 임베딩을 저장합니다.
5. 유사도 검색
추천 요청이 들어오면 요청 내용도 임베딩하고, 기존 게시글 벡터와 비교합니다.
6. 근거 필터링
유사도가 낮거나, 재료 연결이 없거나, 댓글 근거가 없는 글은 참고 자료에서 제외합니다.
7. 생성과 저장
선별된 근거와 현재 재료를 LLM에 전달해 추천을 만들고, 추천 결과와 참고 게시글을 저장합니다.

이 프로젝트에서 RAG 데이터로 무엇을 쓰는가

데이터 RAG에서의 의미 주의할 점
게시글 제목 사용자가 어떤 문제나 상황을 말하는지 파악하는 힌트 제목만으로 판단하면 맥락이 부족할 수 있습니다.
게시글 본문 질문자의 상황, 보유 재료, 원하는 방향을 담은 문맥 본문은 질문에 가깝기 때문에 레시피 근거로 과신하면 안 됩니다.
댓글 다른 사용자의 실제 조언, 조리 팁, 답변 근거 이 프로젝트에서는 댓글 조언을 커뮤니티 근거로 더 중요하게 봅니다.
태그 재료나 주제를 빠르게 파악하는 분류 정보 태그는 보조 정보이지, 본문과 댓글을 대체하지 않습니다.
조회 수 사용자 관심도를 보여주는 부가 신호 조회 수가 높다고 항상 좋은 근거는 아닙니다.

pgvector를 선택한 이유

벡터 검색을 하려면 Pinecone, FAISS, ChromaDB 같은 별도 벡터 DB를 쓸 수도 있습니다. 하지만 이 프로젝트는 이미 PostgreSQL을 사용하고 있습니다. 그래서 pgvector를 쓰면 게시글 데이터와 벡터 데이터를 같은 DB 안에서 관리할 수 있습니다.

  • ✓
    별도 벡터 DB 서버를 추가하지 않아도 됩니다.
  • ✓
    게시글, 댓글, 추천 결과와 벡터 근거를 같은 트랜잭션/관계 안에서 추적하기 쉽습니다.
  • ✓
    과제 규모에서는 아키텍처가 과하게 복잡해지는 것을 막을 수 있습니다.
  • ✓
    나중에 검색 품질이 더 중요해지면 LlamaIndex 같은 오케스트레이션 도구를 추가할 수 있습니다.

COMMUNITY_RAG와 GENERAL_AI

RAG에서 중요한 태도는 “근거가 없으면 없다고 말하는 것”입니다. 비슷한 게시글이 없는데도 커뮤니티를 참고했다고 말하면 사용자를 속이는 결과가 됩니다.

상태 의미 사용자에게 보여줄 설명
COMMUNITY_RAG 유사한 커뮤니티 게시글과 댓글을 1개 이상 근거로 사용한 추천 “비슷한 커뮤니티 글과 댓글을 참고한 추천입니다.”
GENERAL_AI 쓸 만한 커뮤니티 근거가 없어 현재 입력과 일반 요리 지식으로 만든 추천 “현재 입력과 일반 요리 지식을 기준으로 만든 추천입니다.”

RAG에서 자주 생기는 문제

문제 왜 생기는가 설계 대응
엉뚱한 게시글이 근거로 잡힘 문장 분위기는 비슷하지만 실제 재료가 다를 수 있습니다. 유사도 기준과 최소 재료 겹침 기준을 함께 둡니다.
추천 근거가 너무 약함 게시글은 있지만 댓글 조언이 없을 수 있습니다. 댓글 근거가 없는 글은 커뮤니티 근거로 쓰지 않습니다.
오래된 추천이 계속 보임 게시글이나 댓글이 수정되면 이전 추천의 근거가 달라질 수 있습니다. 관련 글/댓글이 바뀌면 추천을 stale 상태로 보고 다시 추천하게 합니다.
첫 사용자는 근거가 없음 커뮤니티 데이터가 아직 적기 때문입니다. 실패로 처리하지 않고 GENERAL_AI로 분리해 정직하게 표시합니다.
RAG를 설명할 때 가장 중요한 문장: “AI가 답하기 전에 우리 서비스의 게시글과 댓글을 먼저 검색하고, 그 검색 결과를 근거로 추천을 생성한다.”

MCP 자세히 이해하기

MCP는 Model Context Protocol의 줄임말입니다. 쉽게 말하면 LLM이 외부 시스템을 도구처럼 사용할 수 있도록 만드는 약속입니다.

왜 MCP가 필요한가

LLM은 문장을 잘 만들지만, 그 자체로는 외부 API를 안전하게 호출하거나, API Key를 관리하거나, 외부 서비스의 응답 형식을 표준화하지 못합니다. MCP는 이런 외부 기능을 “도구 목록”으로 제공하고, LLM이나 Agent가 필요한 도구를 호출할 수 있게 해줍니다.

이 프로젝트에서는 공공 식품 영양정보 API가 외부 시스템입니다. 사용자가 “계란, 두부, 대파”를 입력하면, AI가 감으로 영양정보를 말하는 것이 아니라 MCP 도구를 통해 실제 메타데이터를 조회할 수 있습니다.

MCP 통신 흐름

initialize
클라이언트가 MCP 서버에게 연결을 시작하고, 서버 정보와 지원 기능을 확인합니다.
tools/list
MCP 서버가 사용 가능한 도구 목록과 각 도구의 입력 형식을 알려줍니다.
tools/call
클라이언트가 특정 도구 이름과 입력값을 보내고, 서버가 결과를 돌려줍니다.
structuredContent
도구 실행 결과를 사람이 읽는 문자열뿐 아니라 구조화된 데이터로도 전달합니다.

JSON-RPC는 어떤 역할인가

JSON-RPC는 요청과 응답을 JSON 형식으로 주고받기 위한 규칙입니다. 핵심은 “어떤 method를 호출할지”, “어떤 params를 넘길지”, “그 요청의 id가 무엇인지”를 명확히 적는 것입니다.

필드 의미 예시 감각
id 요청과 응답을 연결하는 번호 “내가 보낸 3번 요청에 대한 답이구나”
method 실행하고 싶은 동작 이름 initialize, tools/list, tools/call
params 동작에 필요한 입력값 도구 이름, 음식 이름, 재료 목록
result 성공했을 때의 응답 도구 목록이나 영양정보 결과
error 실패했을 때의 응답 없는 도구, 잘못된 입력, 내부 오류

우리 프로젝트의 MCP 도구

도구 하는 일 AI 기능에서의 의미
search_food_items 한국어 음식명으로 공공 데이터 후보를 검색합니다. 사용자 입력이 실제 데이터에 있는 음식인지 후보를 찾습니다.
get_food_nutrition 특정 음식의 영양정보를 가져옵니다. AI가 재료의 칼로리, 단백질, 나트륨 같은 사실 정보를 참고할 수 있습니다.
analyze_ingredients_nutrition 여러 재료를 한 번에 분석하고 합계/평균을 요약합니다. 게시글 작성 보조 Agent가 재료 기반 피드백을 만들 때 사용할 수 있습니다.

MCP의 경계가 중요한 이유

MCP 도구가 할 일과 하지 말아야 할 일을 구분해야 시스템이 안정적입니다. 이 프로젝트에서 식품 메타데이터 MCP는 음식 데이터를 제공하는 역할입니다. 메뉴를 최종 결정하거나, 레시피를 생성하거나, 커뮤니티 근거를 주장하는 역할은 아닙니다.

할 수 있음: 음식명 정규화 할 수 있음: 영양정보 조회 할 수 있음: API 오류 보고 하면 안 됨: 최종 메뉴 결정 하면 안 됨: 조리법 생성 하면 안 됨: 커뮤니티 근거 주장

API Key와 권한 관리

외부 API Key는 프론트엔드에 두면 안 됩니다. 브라우저에 노출되는 순간 누구나 그 키를 볼 수 있기 때문입니다. 그래서 API Key는 백엔드 또는 MCP 서버의 환경변수로 관리하고, 프론트엔드는 백엔드에 요청만 보내는 구조가 안전합니다.

  • ✓
    API Key는 서버 환경변수에 둡니다.
  • ✓
    로그에는 API Key를 출력하지 않습니다.
  • ✓
    키가 없을 때는 서버가 터지는 대신 configuration_missing 같은 상태를 돌려줍니다.
  • ✓
    외부 API 장애나 rate limit은 api_error 같은 구조화된 상태로 처리합니다.

MCP에서 자주 생기는 문제

문제 왜 중요한가 대응 방식
입력값이 비어 있음 외부 API에 의미 없는 요청을 보내게 됩니다. 도구 입력 스키마와 서버 검증으로 막습니다.
음식명이 여러 후보와 매칭됨 AI가 잘못된 영양정보를 참고할 수 있습니다. 후보 목록과 matchStatus를 함께 돌려줍니다.
외부 API 장애 AI 기능 전체가 실패한 것처럼 보일 수 있습니다. 도구 실패를 구조화하고, 사용자에게는 제한적으로 안내합니다.
도구 책임이 커짐 MCP가 추천 생성까지 맡으면 RAG/Agent와 책임이 섞입니다. MCP는 사실 데이터 제공까지만 맡도록 경계를 둡니다.
MCP를 설명할 때 가장 중요한 문장: “LLM이 직접 알 수 없는 외부 식품 영양정보를, 표준화된 도구 호출 방식으로 안전하게 가져오도록 만든 구조다.”

RAG와 MCP가 함께 쓰이는 방식

RAG와 MCP는 경쟁 관계가 아닙니다. 이 프로젝트에서는 서로 다른 근거를 제공하는 두 축으로 같이 사용됩니다.

AI 레시피 추천을 예로 보기

  1. 1
    사용자 입력
    사용자가 게시글 또는 직접 입력으로 보유 재료와 상황을 제공합니다.
  2. 2
    RAG 검색
    비슷한 게시글과 댓글 조언을 찾아 커뮤니티 근거를 확보합니다.
  3. 3
    MCP 메타데이터
    재료의 영양정보를 외부 공공 데이터에서 조회합니다.
  4. 4
    LLM 생성
    커뮤니티 근거와 식품 메타데이터를 함께 참고해 추천 결과를 만듭니다.
  5. 5
    결과 저장
    추천 내용, 참고 게시글, grounding 상태, 썸네일 등을 저장합니다.
구분 RAG MCP
데이터 성격 서비스 내부 커뮤니티 데이터 외부 공공 식품 데이터
질문 이 사용자 상황과 비슷한 글이 있었나? 이 재료의 실제 영양정보는 무엇인가?
결과 참고 게시글, 댓글 조언, 유사도 음식 후보, 영양성분, 매칭 상태
실패 시 GENERAL_AI로 정직하게 분리 configuration_missing, not_found, api_error 등으로 구조화
발표나 README에서 이렇게 말하면 좋습니다. “RAG는 우리 게시판 안의 경험을 찾고, MCP는 외부 식품 데이터를 가져옵니다. LLM은 이 두 근거를 조합해 추천을 생성합니다.”

시나리오 문제

정답이 하나로 딱 떨어지는 문제보다, 흐름을 설명해보는 연습이 백엔드 공부에 더 도움이 됩니다.

상황 1

사용자가 게시글을 수정했습니다. 그런데 이 게시글을 근거로 예전에 만들어둔 AI 추천 결과가 있습니다. 이 추천 결과를 그대로 최신 정보라고 보여줘도 괜찮을까요?

상황 2

어떤 사용자가 로그인은 했지만, 다른 사람이 작성한 댓글을 삭제하려고 합니다. 서버는 어떤 기준으로 이 요청을 막아야 할까요?

상황 3

README에 RAG, MCP, Agent를 모두 구현했다고 적으려고 합니다. 단순히 기술명을 나열하는 대신, 각각을 어떤 사용자 기능과 연결해서 설명하면 좋을까요?

상황 4

사용자가 “계란이랑 두부가 있는데 뭐 해먹을까?”라고 입력했습니다. 이때 RAG는 어떤 정보를 찾고, MCP는 어떤 정보를 가져오면 좋을까요?

상황 5

유사도 검색 결과는 나왔지만, 비슷한 게시글에 댓글 조언이 하나도 없습니다. 이 글을 COMMUNITY_RAG 근거로 써도 될까요?

상황 6

식품 공공 데이터 API Key가 설정되지 않았습니다. MCP 도구는 서버를 바로 죽이는 대신 어떤 식으로 응답하는 것이 좋을까요?

상황 1 가이드 게시글 내용이 바뀌면 그 글을 근거로 만든 추천 결과도 오래된 정보가 될 수 있습니다. 그래서 추천 결과를 다시 만들거나, 최소한 최신 근거가 아닐 수 있다는 상태를 관리하는 것이 좋습니다.
상황 2 가이드 로그인 여부와 권한은 다릅니다. 서버는 토큰으로 사용자를 확인한 뒤, 댓글의 작성자 ID와 요청한 사용자 ID가 같은지 비교해야 합니다.
상황 3 가이드 RAG는 유사 게시글 기반 추천, MCP는 외부 식품 영양정보 조회, Agent는 게시글 초안 작성 보조처럼 사용자가 실제로 경험하는 기능과 연결해서 설명하면 좋습니다.
상황 4 가이드 RAG는 계란/두부와 비슷한 재료 상황의 기존 게시글과 댓글 조언을 찾습니다. MCP는 계란과 두부의 실제 영양정보, 후보 매칭 상태, 단백질이나 나트륨 같은 메타데이터를 가져옵니다.
상황 5 가이드 댓글 조언이 없다면 커뮤니티의 실제 답변 근거가 약합니다. 이 경우 COMMUNITY_RAG라고 주장하기보다 GENERAL_AI로 분리하거나, 근거 부족 상태를 사용자에게 정직하게 보여주는 편이 좋습니다.
상황 6 가이드 API Key가 없을 때는 서버가 갑자기 죽는 것보다 configuration_missing 같은 구조화된 상태를 반환하는 것이 좋습니다. 그래야 Agent나 백엔드가 실패를 해석하고 대체 흐름을 선택할 수 있습니다.
